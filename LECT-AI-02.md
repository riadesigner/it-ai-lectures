## Что такое temperature и как это настраивать?

**Короткий ответ**

**Temperature** (температура) — параметр LLM, который управляет **случайностью** выбора следующего слова (токена). Чем выше температура, тем разнообразнее и «смелее» ответ; чем ниже — тем стабильнее и предсказуемее.

Модель на каждом шаге считает вероятности для кандидатов. Temperature «размазывает» или «сжимает» эти вероятности перед выбором:

- **низкая** (0–0.3) — почти всегда берёт самый вероятный вариант → точность, повторяемость;
- **средняя** (0.5–0.7) — баланс между стабильностью и вариативностью;
- **высокая** (0.8–1.0+) — чаще выбирает менее вероятные варианты → креатив, но больше «плывёт» и противоречий.


| Temperature  | Когда полезно в gamedev                                 | Риск                                                       |
| ------------ | ------------------------------------------------------- | ---------------------------------------------------------- |
| **0–0.3**    | UI-тексты, JSON, таблицы баланса, чеклисты, GDD-шаблоны | Сухо, однообразно, «шаблонно»                              |
| **0.5–0.7**  | Квесты, NPC-реплики, world bible, brainstorming         | Обычно лучший компромисс                                   |
| **0.8–1.0+** | Идеи названий, необычные механики, mood, «а что если»   | Галлюцинации, несогласованный лор, «каждый раз новая игра» |


**Как настраивать**

1. **API** (OpenAI, Anthropic, DeepSeek и т.д.) — параметр `temperature` в запросе (число, обычно 0–2).
2. **IDE / SDK** (Cursor, свой скрипт) — то же поле в настройках модели или в коде вызова.
3. **Обычный веб-чат** (ChatGPT, Claude в браузере) — temperature **часто спрятан**; пользователь крутит её косвенно через промпт («будь креативнее» / «строго по формату»). Для учебных сравнений лучше показать API или инструмент, где параметр виден явно.

Пример (псевдокод API):

```json
{
  "model": "gpt-4o-mini",
  "messages": [{ "role": "user", "content": "..." }],
  "temperature": 0.7
}
```

**Аналогия:** temperature — «насколько модель рискует». Низкая — дизайнер по брифу; высокая — мозговой штурм без фильтра.

**На курсе:** лекция 3 — temperature **интуитивно**, без формул; практика 3 — A/B: один промпт при `temperature: 0.2` и `0.9`, сравнить quest hook. Фраза для доски: *«Temperature — не „умность“, а „смелость выбора слов“»*.

**Частая ошибка:** крутить temperature вместо правки промпта. Сначала RCTF и итерация; temperature — тонкая настройка, когда структура уже ок.

## Что такое токены (tokens)?

**Короткий ответ**

**Токен** — кусочек текста, с которым работает LLM: не всегда целое слово, чаще слог, часть слова или знак препинания. Модель не «читает абзацы», а **предсказывает следующий токен** по уже набранной цепочке.

Примеры (условно):

- `"игра"` → может быть 1 токен;
- `"геймдизайн"` → часто 2–3 токена;
- `"NPC"` → отдельные токены для букв/кусков.


| Термин             | Простыми словами                                                 |
| ------------------ | ---------------------------------------------------------------- |
| **Токен**          | минимальная «единица текста» для модели                          |
| **Context window** | сколько токенов модель «помнит» в одном запросе (промпт + ответ) |
| **Лимит ответа**   | max tokens — потолок длины генерации                             |


**Зачем gamedev-студенту:** лимит контекста = нельзя скормить весь GDD на 40 страниц одним сообщением. Длинный world bible режут на части или просят краткие секции. Длинный ответ обрывается, если max tokens маленький.

**Грубая оценка для лекции:** 1 токен ≈ ¾ слова в английском; в русском часто **меньше слов на токен** (слова длиннее). Для курса достаточно: *«1000 токенов — примерно 1–2 страницы текста, порядок величины»*.

**Аналогия:** токены — «кубики LEGO текста». Модель собирает фразу кубик за кубиком; вы платите и упираетесь в лимит по числу кубиков, а не по «ощущению длины».

**На курсе:** лекция 1 — термин без математики; лекция 7 — когда GDD режут на секции из‑за контекста. Фраза для доски: *«LLM не знает вашу игру — видит только то, что влезло в окно токенов»*.

## Что такое галлюцинации LLM?

**Короткий ответ**

**Галлюцинация** — когда модель выдаёт **уверенный, гладкий текст, который звучит правдоподобно, но неверен**: выдуманные факты, несуществующие механики, «цитаты» из игр, противоречия внутри одного ответа, числа баланса без опоры на ваш дизайн.

Это не «баг сети» и не «модель сошла с ума». LLM **генерирует правдоподобное продолжение**, а не проверяет факты в базе данных игр.

Типичные случаи в gamedev:

- «В Dark Souls есть механика X» — X выдуман;
- таблица урона с «красивыми» числами, но без связи с вашим core loop;
- NPC помнит событие, которого не было в вашем лоре;
- JSON с лишней запятой или полем — «галлюцинация формата».


| Как снижать риск              | Пример                                  |
| ----------------------------- | --------------------------------------- |
| Конкретный контекст в промпте | «Только наш сеттинг: …»                 |
| Формат + ограничения          | «Таблица из 5 строк, без новых фракций» |
| Низкая temperature            | UI, числа, структура                    |
| Промпт-критик                 | «Найди противоречия с world bible выше» |
| **Ручная правка**             | ИИ — черновик, не финал                 |


**Аналогия:** очень красноречивый напарник на брейншторме, который иногда уверенно врёт — идеи брать можно, факты проверять обязательно.

**На курсе:** лекция 1 — термин «галлюцинации»; лекция 4 — клише и «generic fantasy»; лекция 7 — не копипастить raw AI в прод/GDD без редактуры. Фраза для доски: *«Уверенный тон ≠ правда»*.

**Частая ошибка студента:** принять первый красивый ответ за канон лора. В практиках — чеклист «что я проверил руками».

## Что такое RCTF?

**Короткий ответ**

**RCTF** — учебный **шаблон структуры промпта** на этом курсе (не общепринятый мировой стандарт, а удобная «опора для доски»). Аббревиатура от четырёх блоков + пятый, который всегда добавляем рядом:


| Буква | Блок                          | Что писать                                                |
| ----- | ----------------------------- | --------------------------------------------------------- |
| **R** | **Role** (роль)               | Кем «быть» модели: «ты — гейм-дизайнер жанра X»           |
| **C** | **Context** (контекст)        | О какой игре речь: жанр, платформа, аудитория, референсы  |
| **T** | **Task** (задача)             | Что сделать **конкретно**: «опиши side-quest на 15 минут» |
| **F** | **Format** (формат)           | Как отдать ответ: список, таблица, JSON, 5 абзацев        |
| *(+)* | **Constraints** (ограничения) | Лимит слов, тон, табу: «без новых фракций», «без клише»   |


**Зачем:** плохой промпт типа «придумай квест» → размытый ответ. RCTF заставляет заранее ответить на вопросы модели: *кто ты, о чём игра, что именно нужно, в каком виде, чего нельзя*.

**Шаблон для студентов:**

```
Role: Ты — опытный гейм-дизайнер [жанр].
Context: Мы делаем [игра, платформа, аудитория, референсы].
Task: [конкретная задача].
Format: [список / таблица / JSON / абзацы].
Constraints: [лимит слов, тон, что нельзя].
```

**Пример (квест):**

```
Role: Ты — narrative designer RPG в духе Disco Elysium.
Context: PC, single-player, сеттинг — постапокалиптический порт, аудитория 16+.
Task: Side-quest на 15–20 мин: игрок помогает смотрителю маяка.
Format: название, синопсис (3 предложения), 4 шага геймплея, награда.
Constraints: без новых NPC-квестодателей; тон мрачный, но без gratuitous (безпричинное) violence; до 200 слов.
```

**Аналогия:** RCTF — **ТЗ для фрилансера**. Без ТЗ получите «красиво, но не то»; с ТЗ — правки предсказуемее.

**На курсе:** лекция 2 — вводим; практика 2 — переписываем 5 плохих промптов по RCTF. Фраза для доски: *«RCTF — не магические слова, а чеклист: модель не телепат»*.

**Не путать:** RCTF ≠ единственный формат в индустрии. В других гайдах встретятся CRISPE, CO-STAR и т.п. — смысл тот же: роль, контекст, задача, формат, ограничения.

**Частая ошибка:** набить Context простынёй на 2 страницы и потерять Task. Контекст — ровно столько, сколько нужно для задачи.

## Пример плохого и хорошего промпта для описания игрового мира

**Короткий ответ**

Одна и та же задача («опиши игровой мир») — два промпта. Разница в результате огромная.

### Плохой

```
Придумай игровой мир для игры.
```

**Почему плохо:** нет жанра, тона, аудитории, формата и ограничений. Модель выдаст generic fantasy — красиво, но без опоры для дизайна.

### Хороший (RCTF) – (Role, Context, Task, Format, +Constrains)

```
Role: Ты — narrative (повествование) designer с опытом в indie-RPG.

Context: Делаем single-player RPG на PC для аудитории 16+.
Референсы по атмосфере: Disco Elysium + Outer Wilds.
Игрок — младший архивариус в городе на краю исчезающего моря.
Жанр: investigation + исследование, без боевой системы как ядра.

Task: Опиши игровой мир на уровне world bible (macro):
история в 1 абзаце, текущий конфликт, 2 фракции, 3 правила мира,
которые влияют на геймплей, одна ключевая локация.

Format:
1) Название мира (3 варианта)
2) Синопсис мира (до 80 слов)
3) Конфликт (до 40 слов)
4) Фракции: таблица [название | цель | отношение к игроку]
5) Правила мира: нумерованный список из 3 пунктов
6) Ключевая локация: название + 3 предложения

Constraints:
- без эльфов, орков и «избранного героя»;
- тон: меланхоличный, ироничный;
- не предлагай механики боя и уровни персонажа;
- не раздувай лор: только то, что нужно для квестов и диалогов.
```

**Почему хорошо:** роль, контекст, конкретная задача, жёсткий формат и запреты. Ответ можно сразу править и класть в world bible.

**Аналогия / фраза для доски:** плохой промпт просит «что-нибудь красивое»; хороший — даёт ТЗ дизайнеру.

**На курсе:** лекция 1 — live-demo «плохой vs хороший» на описании мира; лекция 2 / практика 2 — те же примеры через RCTF.

**Частая ошибка:** после хорошего промпта принять raw-ответ за финальный канон. Всегда ручная правка.

## Чем чат отличается от инструмента?

**Короткий ответ**

Одна и та же LLM может работать в двух режимах:


|               | **Чат**                            | **Инструмент**                                                  |
| ------------- | ---------------------------------- | --------------------------------------------------------------- |
| **Что это**   | Диалог «спросил — ответил»         | Часть рабочего процесса: задача → промпт → артефакт → правка    |
| **Цель**      | Поболтать, быстро набросать идею   | Получить **рабочий кусок** для проекта (квест, NPC, секция GDD) |
| **Промпт**    | Часто короткий, без формата        | RCTF, ограничения, итерации                                     |
| **Результат** | «Интересно почитать»               | Файл / таблица / sheet, который идёт дальше                     |
| **Отношение** | Модель = собеседник                | Модель = ассистент на конкретной задаче                         |
| **Риск**      | Приятный текст без пользы для игры | Меньше риска «утонуть в болтовне», если есть формат             |


**Чат** — окно переписки (ChatGPT, Claude, DeepSeek Chat). Удобно думать вслух, уточнять, брейнштормить.

**Инструмент** — когда вы **осознанно** используете ту же модель как станок: есть бриф, формат ответа, критерий «готово / не готово», ручная редактура. Тот же чат становится инструментом, если вы так работаете.

Позже «инструмент» ещё и буквально: API, Cursor, генератор картинок, скрипт с `temperature` — модель встроена в пайплайн, а не только в браузерный диалог. Коротко – **разговор vs целенаправленная работа**.

**Аналогия:** чат — разговор с коллегой у кофемашины; инструмент — тот же коллега, которому вы дали ТЗ и дедлайн на 1 страницу world bible.

**Фраза для доски:** *«Окно одно — навык разный: болтать или производить»*.

**На курсе:** лекция 1 — базовые понятия; дальше практики требуют режим «инструмент» (таблица промптов, артефакты, чеклисты). Prompt-инжиниринг как раз учит переключаться из чата в инструмент.

**Частая ошибка:** час «интересного диалога» без сохранения структуры → к концу пары нечего сдать. Правило: после 2–3 сообщений зафиксировать артефакт.

## Что ИИ не заменяет?

**Короткий ответ**

Для лекции 1, блок «Контекст индустрии»:

1. **Вкус дизайнера** — что «играбельно», что скучно, что соответствует pillars игры. Модель предлагает варианты; выбор и отсев — за человеком.
2. **Ответственность за финал** — канон лора, баланс, тексты в билде. Raw AI без редактуры в прод не идёт.
3. **Игровой опыт игрока** — playtest, ощущение pacing, «весело ли». ИИ не сыграет за игрока и не почувствует фрустрацию.
4. **Командное согласование** — переговоры с арт/продюсером, скоуп, приоритеты. Документ пишет ИИ — решения принимает команда.

**Фраза для доски:** *«ИИ ускоряет черновик. Дизайнер отвечает за игру.»*

**На курсе:** лекция 1 — тезисы курса; лекция 7 — anti-patterns (финальный lore без редактуры, копипаст в прод).

## Правила

**Как не раздувать файл**

- Сюда — в первую очередь **краткий ответ** (5–15 строк). Длинные разборы — только если без них нельзя.
- Оглавление ниже: искать по нему, не листать весь файл.
- Когда записей станет много (ориентир: 15–20) — разрежем на `teacher-faq-basics.md`, `teacher-faq-gamedev.md` и т.п., а здесь оставим оглавление со ссылками. Пока один файл нормален.

Порядок: **от более общих к более частным** (как шли вопросы). Новые — в конец, перед шаблоном.
